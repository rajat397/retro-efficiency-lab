## 1. The formula / code path

Call chain, once per game tick:

`GameState.cpp:329` (`Park::Update(park, gameState)`) → `world/Park.cpp:353`
(`generateGuests`) → `world/Park.cpp:223` / `world/Park.cpp:242` (`GenerateGuest` →
`Guest::generate`).

### 1.1 Per-tick stochastic roll — `src/openrct2/world/Park.cpp:215-238`

```cpp
static void generateGuests(ParkData& park, GameState_t& gameState)
{
    // Generate a new guest for some probability
    if (static_cast<int32_t>(ScenarioRand() & 0xFFFF) < park.guestGenerationProbability)
    {
        bool difficultGeneration = park.flags.has(ParkFlag::difficultGuestGeneration);
        if (!difficultGeneration || park.suggestedGuestMaximum + 150 >= park.numGuestsInPark)
        {
            GenerateGuest();
        }
    }
    // Extra guests generated by advertising campaigns
    for (const auto& campaign : park.marketingCampaigns) { ... }
}
```

So `guestGenerationProbability` is a probability out of 65535 checked every game tick
via one random draw. The comment at `src/openrct2/world/ParkData.h:102-107` states the
intended law explicitly: "new guests per second = 40 * (probability / 65535)"; with a
full park rating, non-overpriced fee, sub-cap guest count, and four positive awards,
approximately 1 guest/second (+60 guests/minute).

### 1.2 The probability formula — `src/openrct2/world/Park.cpp:163-213`

```cpp
// Begin with 50 + park rating
uint32_t probability = 50 + std::clamp(park.rating - 200, 0, 650);

// The more guests, the lower the chance of a new one
uint32_t numGuests = park.numGuestsInPark + park.numGuestsHeadingForPark;
if (numGuests > park.suggestedGuestMaximum)
{
    probability /= 4;
    if (park.flags.has(ParkFlag::difficultGuestGeneration))
        probability /= 4;
}

// Reduces chance for any more than 52000 guests
if (numGuests > 52000)
    probability /= 4;

// Penalty for overpriced entrance fee relative to total ride value
auto entranceFee = GetEntranceFee(park);
if (entranceFee > park.totalRideValueForMoney)
{
    probability /= 4;
    if (entranceFee / 2 > park.totalRideValueForMoney)
        probability /= 4;
}

// Reward or penalties for park awards  (+/- 25% per positive/negative award)
for (const auto& award : park.currentAwards)
{
    if (AwardIsPositive(award.type))
        probability += probability / 4;
    else
        probability -= probability / 4;
}
```

## 2. Control-loop shape

This is a **two-timescale negative-feedback loop**, not free-running growth.

**Fast layer (every tick):**
- Rate input: `park.guestGenerationProbability` (ParkData.h:108), recomputed only
  periodically; the tick merely draws against it (Park.cpp:218).
- Campaign additive term: per active campaign, a fixed table probability
  (`management/Marketing.cpp:48-51`, table `{400, 300, 200, 200, 250, 200}`) with
  per-campaign dampers, e.g. free-entry ads divide by 8 when the entrance fee is
  already cheap (`Marketing.cpp:63-66`).

**Slow layer (every 512 ticks, ~13 s — `world/Park.cpp:334-345`):**
1. `park.rating = CalculateParkRating(park, gameState)` (Park.cpp:336; formula at
   Park.cpp:376-490 — guest count/happiness/lost guests at :392-423, ride
   uptime/excitement at :444-474, litter at :478-485, clamped 0..999 at :488).
2. `park.totalRideValueForMoney` (Park.cpp:338; sum of `ride.value * 2` minus prices,
   Park.cpp:75-101).
3. `park.suggestedGuestMaximum = calculateSuggestedMaxGuests` (Park.cpp:339; sum of
   ride-type `BonusValue` over open non-broken rides, Park.cpp:103-161; hard cap
   65535 at :143, difficult-mode cap 1000 + bonus at :139-141).
4. `park.guestGenerationProbability = calculateGuestGenerationProbability` (Park.cpp:340).

**Feedback edges (the "measured slowdown" wiring):**
- Guest population ↑ above `suggestedGuestMaximum` → probability ÷4 (Park.cpp:170-178);
  hard spawn refusal in difficult mode when `suggestedGuestMaximum + 150 < numGuestsInPark`
  (Park.cpp:221).
- Guest population ↑ (they generate the litter and unhappy-lost-guest counts that feed
  `CalculateParkRating`) → rating ↓ → probability base `50 + clamp(rating-200,0,650)` ↓
  (Park.cpp:166).
- Entrance fee ↑ relative to ride value → ÷4 or ÷16 (Park.cpp:187-196).
- Positive awards → +25% of current probability each; negative awards → −25%
  (Park.cpp:199-210).

**Historical delta layer (weekly):** `UpdateHistories` (Park.cpp:566-613) computes
`changeInGuestsInPark = numGuestsInPark - numGuestsInParkLastWeek` (Park.cpp:569-570)
and maps it to `park.guestChangeModifier ∈ {0,1,2}` (Park.cpp:568-579): +1 step if
change > −20, reset to 0 if change < 20, i.e. 2 = strong growth, 1 = mild
decline/growth, 0 = flat. Note: in this build `guestChangeModifier` is computed and
serialized (`ParkFile.cpp:1083`) but the in-game consumer of the modifier could not be
anchored (see §5); the legacy struct field maps to `_s6.GuestCountChangeModifier`
(`rct2/RCT2.h:864`, imported at `rct2/S6Importer.cpp:397`).

## 4. Mechanism assessment — M-5 "measured slowdown"

**Fit: good, with one caveat.**

What matches M-5 precisely:
- The spawn rate is a *measured, modulated variable* (`guestGenerationProbability` is
  recomputed from live measurements every 512 ticks), not a free-running growth
  constant. The measurement inputs are the guest population delta against a
  ride-derived ceiling (`suggestedGuestMaximum`), the park rating (itself derived from
  measured counts: happy guests, lost guests, litter age ≥ 7680 ticks), the fee-to-
  ride-value ratio, and award state.
- The modulation is strictly *negative feedback against a soft ceiling*: overshoot
  divides the rate by 4 (and by 16 in difficult mode), producing the classic measured
  slowdown curve rather than a hard population stop — a cap-squeeze/throttle law
  typical of 90s simulation economics.
- Park rating forms a second, slower negative loop: guests themselves generate the
  litter and lost-guest counts that depress rating, which depresses the base rate.
- The `Guest::generate` free-entity veto (< 400 free entities) is a hard resource
  brake layered under the soft rate law — exactly the bounded-resource family this
  lab catalogs.

Caveat / weaker fit:
- The weekly `guestChangeModifier` (Park.cpp:568-579) is the closest analogue to the
  original `GuestCountChangeModifier` variable named in the mission brief, but in this
  codebase it appears to be write-only bookkeeping (computed weekly, saved, no in-tree
  consumer found during the probe). If the lab expects guest-count *delta* to
  directly modulate spawn rate per tick, that is not how OpenRCT2's port works: the
  delta influences spawn rate only indirectly (it shows up in peep thoughts / UI
  warnings in the original; here its consumer is unanchored). The dominant modulation
  is absolute population vs. suggested maximum, not the delta.
